# bot-home — скелет изолированного agent dir бота

Каталог — эталон домашнего окружения бота: персона, настройки и регистрация MCP.
На рабочую машину он не копируется руками, а разворачивается скриптом
`../provision-agent.sh AGENT_DIR [CODE_DIR]` (идемпотентно).

## Состав

- `AGENTS.md` — персона участника чата: кто такой бот, как он говорит, кого считает
  владельцем и что делает с его командами. Различение «команда владельца vs болтовня»
  живёт только здесь, не в коде демона. Это и есть файл, который правят под своего бота.
- `settings.json` — дефолты бота: thinking `low` и выключенный builtin `ttsr`.
- `mcp.json` — единственный MCP-сервер `tg-chat` (только чтение истории/поиск/медиа).
  Содержит шаблонные placeholders и правится только скриптом:
  - `__CODE_DIR__` — абсолютный путь этого чекаута; бинарь берётся как
    `__CODE_DIR__/target/release/tg-chat` (после `cargo build --release`);
  - `__STATE_DIR__` — `CHATBOT_STATE_DIR` работающего демона (абсолютный путь);
  - `__CHAT_ID__` — `CHATBOT_CHAT_ID` (тот же чат, что у демона);
  - `__TOKEN_FILE__` — `CHATBOT_TOKEN_FILE` (файл с токеном, mode 600).

  Скрипт требует `CHATBOT_TOKEN_FILE` и `CHATBOT_CHAT_ID` из окружения и падает, если чего-то
  нет: путь под наш сервер или чужой чат по умолчанию не подставляется никогда.
  `CHATBOT_STATE_DIR` берётся из окружения, а без него — `<CODE_DIR>/state`.

- Сюда же вручную кладутся (не коммитятся, mode 600): `auth.json`, `models.json`.

## Чего здесь нет и не должно быть

`rules/*.json` (control_task, ремайндеры, таск-цикл), хук-конфиги, чужие MCP,
профили реальных людей из чата. Глобальные `~/.omo` не трогаем.

## Один поллер

`getUpdates` дёргает только демон (`chatd run`, ключ `offset` в state-каталоге).
Зеркало `tg-chat` только читает базу (лаг = окно батча). Второй опросчик
недопустим: Bot API подтверждает offset глобально на бота, и два консумера
подтверждают друг другу потерянные сообщения.
