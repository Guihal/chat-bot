# chat-bot — демон-участник Telegram-чата

Бот, который живёт в вашем Telegram-чате как обычный собеседник: читает сообщения группы,
отвечает от своего имени и, если вы разрешите, выполняет ваши поручения как агент `omo`
в изолированной сессии.

Как это устроено: Bot API с одной стороны, одна долгоживущая host-сессия `omo` — с другой.
Демон `chatd` держит локальный сервер на unix-сокете `<state>/control.sock`; экстеншн
`chat-ext.mjs` сам подключается к нему, получает пачки строками JSON и отвечает исходом
приёма (идемпотентно по `delivery_id`). Файлов inbox нет вообще. Единственный способ
что-то отправить в чат — тул `chat_send` этого экстеншна; ход без его вызовов означает
молчание. Бинарь `tg-chat` — только чтение (история, поиск, медиа, статистика).

## Что понадобится

- `ffmpeg` в PATH — из него демон делает кадры-превью для гифок и видео; без него в контексте останутся пометки «preview unavailable».

- Rust (stable, `cargo`) и Node.js — для сборки и `node --check`.
- `omo` в `PATH` (пакет `omo-ai`): демон поднимает им хост-сессию бота.
- Токен бота от [@BotFather](https://t.me/BotFather).
- Групповой чат, куда добавлен бот, с правом писать.
- Ваш собственный Telegram-аккаунт — «владелец»: только по его прямой просьбе бот
  запускает субагентов.

## Быстрый старт: от клона до работающего бота

1. **Собрать и проверить.**

   ```bash
   git clone <этот-репозиторий> chat-bot && cd chat-bot
   cargo build --release
   cargo test --workspace
   node --check chat-ext.mjs
   ```

2. **Завести своего бота.** В @BotFather: `/newbot`, имя, username. Полученный токен
   положить в файл **с правами 600** — одной строкой, без кавычек и переводов строк
   (демон отказывается читать файл, доступный группе или всем):

   ```bash
   install -m 600 /dev/null ~/.config/chat-bot/bot_token
   printf '%s\n' '123456789:AA...ваш-токен' > ~/.config/chat-bot/bot_token
   ```

3. **Завести свою группу.** Создайте группу, добавьте туда бота, и обязательно выключите
   privacy mode: @BotFather → `/setprivacy` → выберите бота → `Disable`. Иначе бот не увидит
   обычные сообщения чата, а только упоминания.

4. **Узнать chat id.** Напишите что-нибудь в группе (или упомяните бота) и спросите Bot API:

   ```bash
   TOKEN="$(cat ~/.config/chat-bot/bot_token)"
   curl -s "https://api.telegram.org/bot$TOKEN/getUpdates" | head -c 2000
   ```

   Идентификатор группы — поле `result[].message.chat.id`, оно отрицательное и обычно
   начинается с `-100`.

5. **Заполнить окружение.** Скопируйте `env.example` в `.env`, подставьте свой токен,
   свой chat id и свой username владельца:

   ```bash
   cp env.example .env
   $EDITOR .env
   set -a; . ./.env; set +a
   ```

   Обязательных переменных ровно две — `CHATBOT_TOKEN_FILE` и `CHATBOT_CHAT_ID`; без них
   демон завершается с ошибкой, называющей недостающую переменную, и ничего никуда не шлёт.

6. **Запустить.**

   ```bash
   ./target/release/chatd run
   ```

   По желанию перед этим можно выгрузить историю чата и собрать саммари:

   ```bash
   ./target/release/chatd sync       # выгрузить историю через getUpdates
   ./target/release/chatd summarize  # chat-summary.md через отдельную сессию
   ./target/release/chatd run        # основной цикл
   ```

Дальше бот отвечает в чате сам. `Ctrl+C` останавливает демон; состояние (история, offset,
квитанции) лежит в `CHATBOT_STATE_DIR` и переживает перезапуск.

## Переменные окружения

Обязательные:

| Переменная | Значение |
|---|---|
| `CHATBOT_TOKEN_FILE` | путь к файлу с токеном, mode 600; значение читается целиком и обрезается |
| `CHATBOT_CHAT_ID` | id чата, который бот обслуживает, например `-1001234567890` |

Остальные (у всех — разумный портативный дефолт):

| Переменная | По умолчанию | Значение |
|---|---|---|
| `CHATBOT_OWNER_USERNAME` | пусто | ваш username без `@`; пусто = никто не может запускать субагентов |
| `CHATBOT_OWNER_ID` | `0` | числовой id владельца — запасной признак для аккаунта без username |
| `CHATBOT_USERNAME` | пусто | username самого бота: по нему определяется обращение `@бот` |
| `CHATBOT_STATE_DIR` | `./state` | `history.db`, `media/`, `events.jsonl`, `chatd.log`, `control.sock` |
| `CHATBOT_SESSION` | `chat-participant` | имя host-сессии, которую ведёт демон |
| `CHATBOT_HOST_SOCKET` | `<state>/host/rpc.sock` | сокет выделенного хоста бота (см. ниже) |
| `CHATBOT_CWD` | `.` | рабочий каталог агентской сессии |
| `CHATBOT_AGENT_DIR` | пусто | изолированный agent dir бота (см. «Сделать своим») |
| `CHATBOT_SYSTEM` | `system-prompt.md` | системный промт сессии |
| `CHATBOT_BATCH_SEC` | `10` | окно батчинга сообщений перед пушем в сессию |
| `CHATBOT_API_BASE` | `https://api.telegram.org` | адрес Bot API (меняется только для тестов) |
| `CHATBOT_SUBAGENT_MODEL` | текущая модель | модель одноразового субагента (`omo -p --model …`) |
| `CHATBOT_ADMIT_FIRST_SEC` | `8` | первый интервал повтора пуша при отказе приёма |
| `CHATBOT_ADMIT_SEC` | `10` | дальнейшие интервалы повтора пуша |
| `CHATBOT_TURN_SEC` | `420` | бюджет хода сессии до решения «зависла» |
| `CHATBOT_TURN_EXTRA_SEC` | `420` | продление, пока агент реально работает |
| `CHATBOT_RETRY_SEC` | `60` | пауза перед повтором неудавшейся доставки |
| `CHATBOT_EMIT_SEC` | `60` | ожидание следа доставки в транскрипте |
| `CHATBOT_SUMMARY_SESSION` | `chat-summary` | имя сессии для `chatd summarize` |

## Запуск как сервис (systemd)

В репозитории есть шаблон `deploy/chat-bot.service` и пример env-файла
`deploy/chat-bot.env.example`:

```bash
sudo mkdir -p /etc/chat-bot
sudo cp deploy/chat-bot.env.example /etc/chat-bot/chat-bot.env
sudo chmod 600 /etc/chat-bot/chat-bot.env
sudo $EDITOR /etc/chat-bot/chat-bot.env     # токен, chat id, owner, пути
sudo cp deploy/chat-bot.service /etc/systemd/system/chat-bot.service
sudo $EDITOR /etc/systemd/system/chat-bot.service   # WorkingDirectory/ExecStart под свой путь
sudo systemctl daemon-reload
sudo systemctl enable --now chat-bot.service
systemctl is-active chat-bot.service
```

Шаблон подставляет значения только из `EnvironmentFile` — в самом юните наших путей нет.

## Сделать своим

- **Токен и чат** — `CHATBOT_TOKEN_FILE` и `CHATBOT_CHAT_ID`, см. выше. Значения по умолчанию
  в коде отсутствуют намеренно: незаполненная конфигурация должна падать, а не писать
  в чужой чат.
- **Владелец** — `CHATBOT_OWNER_USERNAME` (и/или `CHATBOT_OWNER_ID`). Пока он пуст, диспетч
  субагентов закрыт для всех, и демон пишет об этом предупреждение в `chatd.log`.
  Вызов субагента требует `owner_message_id` из свежей пачки, так что право не переживает
  своё сообщение.
- **Персона** — `bot-home/AGENTS.md`: как бот говорит, кого слушается, что ему запрещено.
  Это единственное место, где живёт «команда владельца vs болтовня». `system-prompt.md` —
  системный промт сессии (тон и скрытность).
- **Изолированный agent dir** (свой `mcp.json`, свои настройки агента, без общего профиля):

  ```bash
  export CHATBOT_STATE_DIR=$PWD/state
  export CHATBOT_TOKEN_FILE=~/.config/chat-bot/bot_token
  export CHATBOT_CHAT_ID=-1001234567890
  ./provision-agent.sh ./state/agent "$PWD"
  export CHATBOT_AGENT_DIR=$PWD/state/agent
  ```

  Скрипт копирует `AGENTS.md` и `settings.json` и подставляет абсолютные пути в `mcp.json`
  (`tg-chat` — только чтение). Файлы авторизации агента (`auth.json`, `models.json`, mode 600)
  кладутся туда вручную: скрипт их не создаёт и не копирует.

  Если изоляция не нужна, `CHATBOT_AGENT_DIR` не задавайте — сессия возьмёт ваш обычный
  agent dir. Тогда зарегистрируйте `tg-chat` сами в `~/.omo/agent/mcp.json`:

  ```json
  { "tg-chat": { "command": "/абсолютный/путь/к/chat-bot/target/release/tg-chat",
                 "env": { "CHATBOT_STATE_DIR": "/абсолютный/путь/к/state",
                          "CHATBOT_CHAT_ID": "-1001234567890",
                          "CHATBOT_TOKEN_FILE": "/путь/к/tg-bot.env" } } }
  ```

- **Медиа и профили.** Картинки/гифки складываются в `state/media/`. Каталог `portraits/`
  (профили собеседников для тула `chatter_*`) в репозитории отсутствует намеренно — он
  собирается из реальной переписки; без него `tg-chat` просто не показывает профили.

## Как устроен демон

`chatd run` — три независимые задачи на одном потоке (`tokio` current_thread + `LocalSet`:
соединения sqlite не `Send`):

- **ingest** — `getUpdates` крутится непрерывно; запись сообщения и скачивание медиа уходят
  в отдельную задачу, поэтому медленная загрузка не тормозит опрос. Батч-окно `CHATBOT_BATCH_SEC`.
- **admit** — единственный владелец control-сокета и жизненного цикла сессии
  (`ensure`/`settle`/`recreate`). Пушит батч строкой `{"push":{"delivery_id","text","deliverAs":"steer"}}`
  и ждёт `result`: `started`, `steered`, `queued`, `already_admitted`. Отказ (`turn_conflict`,
  `held_draft`) — это не доставка: отметка не ставится, пуш повторяется, `track` держит батч
  на своих часах.
- **track** — читает `events.jsonl`, зеркалит квитанции, применяет `compacted`-переотправку,
  закрывает батч и просит `admit` о восстановлении зависшей сессии.

Экстеншн передаёт `expected_turn_id` из admission-gate, поэтому steer попадает в УЖЕ идущий
ход, и публикует `delivery_state` из принятых доставок (`emitted` = запись в транскрипте есть,
`failed` = сессия отказала, нужно повторить). Батч закрывается только по ответу на все его
`message_id`; единственный неотвеченный выход — `settled` после `emitted` (агент видел
и промолчал).

Хост бота — отдельный: демон сам поднимает его командой
`omo host ensure --launch-spec <state>/launch-spec.json --socket <sock>`. Экстеншн грузится
на весь хост, поэтому общий хост с другим ботом недопустим — `chat_send` утёк бы в чужие
сессии. Отсюда и дефолтный сокет внутри state-каталога.

### База

Одно соединение, один выделенный поток `chatdb`, FIFO-очередь (`src/db.rs`): блокирующая
работа sqlite не останавливает `current_thread`-рантайм, который одновременно опрашивает
Telegram и пишет кадры в сокет. Многошаговые операции (дедуп-вставка, `mark_done`,
перегенерация текста) идут одним замыканием и потому атомарны относительно остальных
пользователей базы; паника в замыкании возвращается вызывающему как ошибка, поток
продолжает работу. Индексы создаются идемпотентно при старте, старую базу не ломают.

`src/bin/dbbench.rs` — воспроизводимый замер старых и новых запросов на одном файле в одном
прогоне (фаза «до» — старый SQL без новых индексов, «после» — новый вызов с индексами,
затем сравнение результатов: расхождение = баг, а не ускорение).

## Чего здесь нет и как это получить

| Нет | Почему | Как получить |
|---|---|---|
| `state/` | живая база, медиа, квитанции — данные конкретного чата | создаётся сама при первом запуске; историю забирает `chatd sync` |
| `portraits/` | профили реальных людей | генерируются в вашем чате, в репозиторий не годятся |
| `chat-summary.md` | построен по реальной переписке | `chatd summarize` |
| `*.env`, токены | секреты | свои, mode 600, вне git (см. `.gitignore`) |
| наш systemd-юнит и docker-сборка | привязаны к чужому хосту | `deploy/` — шаблон, `docker`-путь намеренно не включён |

Если вы разворачиваете бота копированием (rsync/scp) — исключайте `.git`
(`rsync --exclude=.git`), чтобы служебная история не уезжала на сервер.

## Если что-то пошло не так

- **Демон сразу завершается** — почти всегда не задана обязательная переменная; текст ошибки
  называет её. Проверьте, что она экспортирована в том же процессе (`.env` сам не читается).
- **`refusing token file with group/other permissions`** — исправьте права: `chmod 600`.
- **Бот молчит** — проверьте, что он в группе, privacy mode выключен, `CHATBOT_CHAT_ID`
  совпадает с id группы, а в `chatd.log` нет отказов приёма.
- **Сообщения «пропадают», когда запущено два процесса** — `getUpdates` подтверждает offset
  глобально для бота: один поллер на токен, второй запрещён.
- **Субагенты не запускаются** — не задан `CHATBOT_OWNER_USERNAME`/`CHATBOT_OWNER_ID`
  (в `chatd.log` будет предупреждение) или запрос был не от владельца.
- **Бинарь не стартует на другой машине** (`GLIBC_* not found`) — соберите его на целевой
  системе: `cargo build --release` там же.
- **Нет episodes профилей/пустой `tg-chat`** — каталог `portraits/` не входит в репозиторий;
  без него чтение работает, профилей просто нет.

## Проверки

```bash
cargo build --release
cargo test --workspace           # юнит-тесты ядра, актора базы и живой smoke демона
node --check chat-ext.mjs
```

`tests/daemon_smoke.rs` — живой прогон: настоящий `chatd run` против фейкового Bot API
со стаб-`omo` в `PATH`; читает `gif_list` через control-сокет, проверяет дедуп входящих
и что чужая транзакция записи не блокирует сокет.
